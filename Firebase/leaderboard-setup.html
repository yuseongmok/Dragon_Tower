유대의 탑 온라인 랭킹

구현 및 로컬 검수 완료 · 운영 Firebase 배포 전

현재 상태

로비의 온라인 랭킹 버튼을 추가했습니다. 상위 100명과 내 최고 기록·전체 순위를 보여줍니다. 서버 연결 전에는 준비 중 안내가 나타납니다. 플레이어 꾸미기나 조련사 이미지는 추가하지 않았습니다.

이 랭킹은 플레이테스트용입니다. 게임은 기기에서 전투를 계산하므로 서버가 실제 플레이 여부까지 증명할 수 없습니다. 화면에도 클라이언트 기록 기반임을 표시합니다.

온라인으로 사용하기 위한 설정

  1. Firebase 프로젝트 dragon-tower-da915에서 Cloud Functions 사용 조건을 확인합니다. Cloud Functions 배포에는 Blaze 요금제가 필요합니다. 이번 작업에서는 결제 연결이나 요금제 변경을 하지 않았습니다. 사용을 결정한 경우 예산 알림도 설정하세요.
  2. Firebase App Check에서 기존 Web 앱을 등록하고 reCAPTCHA v3를 설정합니다. 배포 도메인을 허용하고 공개 사이트 키를 준비합니다. 비밀 키나 서비스 계정 키를 게임에 넣지 않습니다. localhost 테스트는 Firebase 공식 App Check 디버그 토큰 절차를 사용하며 운영 빌드에 디버그 토큰을 넣지 않습니다.
  3. 프로젝트의 Firebase/functions 폴더에서 npm install을 실행합니다. 기존 복구 이메일 함수와 별도로 아래 랭킹 함수 3개만 배포합니다.
cd C:\Users\PC\Dragon_Tower\Firebase
firebase login
firebase deploy --project dragon-tower-da915 --only firestore:rules,functions:onlineLeaderboard,functions:leaderboardNameSync,functions:leaderboardAccountCleanup

최신 firestore.rules가 필요합니다. 이번 규칙은 로컬 Firestore 에뮬레이터에서 컴파일·접근 차단·계정 삭제 조건을 검증했습니다.

  1. Assets/WebGLTemplates/DragonTower/firebase-config.js의 appCheckSiteKey에 공개 사이트 키를 넣고, 배포 확인 후 leaderboardEnabled: true로 변경합니다. 현재는 미배포 기능을 호출하지 않도록 false입니다.
  2. WebGL을 다시 빌드한 뒤 운영 주소에서 서로 다른 테스트 계정 2개로 등록·조회·닉네임 변경·삭제까지 검수합니다. 현재 운영 계정의 기록을 시험용으로 등록하거나 삭제하지 않았습니다.

Cloud Functions 시작 · App Check Web 설정 · localhost 디버그 설정

데이터와 정렬

  • leaderboardPlaytest/{uid}: UID별 최고 기록 1개. playerName, dragonId, dragonName, originalDragonName, bestScore, bestFloor, bestBond, runId, achievedAt, achievedAtMs, rankKey, recordVersion, verification.
  • leaderboardSubmissions/{uid}/runs/{runId}: 중복 재전송 확인용 해시·수신 시각·갱신 여부. 같은 runId를 다른 수치로 다시 보내면 거부합니다.
  • leaderboardLimits/{uid} 및 기존 서버 전용 rate limit: 쓰기·조회 빈도 제한. 매 프레임 조회하지 않습니다.
  • 점수 내림차순 → 층 내림차순 → 유대 내림차순 → 최초 서버 접수 시각 오름차순 → UID 오름차순. 단일 rankKey를 목록 조회와 순위 count 집계에 함께 사용합니다. 조회는 읽기 전용 트랜잭션의 동일 스냅샷을 사용합니다.
  • 동일 UID의 완전히 동점인 기록은 기존 기록을 유지합니다. 오프라인 완료 시 실제 완료 시각을 신뢰할 수 없어 서버 최초 접수 시각을 동점 기준으로 사용합니다.
  • 점수·층·유대·파트너는 하나의 도전에서 함께 갱신됩니다. 별개 도전의 최대값을 섞지 않습니다.
  • 닉네임은 서버 users 프로필의 최신 이름으로 동기화합니다. 변경 후 Firestore 트리거 반영까지 잠깐 지연될 수 있습니다. 드래곤 이름은 기록 당시 이름과 원래 종류를 보존합니다.

제출과 저장

사망 및 기존 80층 완주로 확정된 도전만 저장과 함께 전송 대기에 추가됩니다. 일반 로비 복귀·이어하기는 도전 완료가 아닙니다. 종료 이벤트가 반복되어도 runId로 중복을 막습니다. 실패한 제출은 계정별 기존 저장 슬롯에 남고, 다음 로비 진입 또는 랭킹 새로고침에 재시도합니다. 한 번에 1건을 처리하며 미전송 수를 표시합니다. 다른 계정이나 오프라인 프로필의 기록을 자동 합치지 않습니다.

기존 저장에 대기 목록이 없어도 호환됩니다. 과거 lastRun을 자동 소급 제출하지 않습니다. 이전 버전에서 이관된 진행 기록은 기존 점수와 누적 카운터가 맞지 않으면 거부될 수 있으며 원본 저장은 유지합니다.

서버 검증과 한계

인증 토큰 UID, App Check, 삭제 계정 여부, 알려진 드래곤 ID, 숫자·이름 형식, 층·처치 수 관계, 현재 점수표의 산술 일치, 중복 runId, 최고 기록 비교를 검사합니다. 클라이언트의 직접 점수 쓰기는 차단합니다. 서버 점수표는 현재 ProgressionRewards.asset과 16종 드래곤 데이터를 내보낸 functions/leaderboard-data.json입니다. 게임 데이터가 변경되면 이 스냅샷도 검토해야 합니다.

산술 일치는 실제 전투 검증이 아닙니다. 조작된 클라이언트가 형식에 맞는 카운터를 제출할 수 있습니다. 인증된 이용자의 중복 계정, 허위 처치, 허위 유대, 업적 재주장은 완전히 막지 못합니다. 정식 경쟁 랭킹 공개 전에는 서버 발급 도전 ID·시드, 누적 전투/방 이벤트 수집, 서버 재현 또는 서버 권위형 점수 산출, 계정별 업적 원장, 이상 기록 격리 및 운영 검수가 필요합니다. 이번에는 기존 전투/점수 계산을 바꾸지 않았습니다.

이메일·비밀번호·인증 정보는 랭킹 문서에 포함하지 않습니다. 계정 삭제 시 공개 랭킹은 삭제 배치와 서버 정리 트리거로 제거됩니다. UID 삭제 표식은 늦은 요청의 복구를 막기 위해 남습니다.

검수 결과

  • Unity: 로비 복귀 미제출, 종료 중복 방지, 저장 재로딩, 통신 실패 시 대기 유지, 재시도 확인 후 제거, 100개 행 스크롤 및 내 107위 UI 통과.
  • Firebase Auth/Firestore 에뮬레이터: 계정 2개·토큰 UID 검증, 등록, 낮은 기록 유지, 최고 기록 갱신, 다른 드래곤, 닉네임 동기화, top100 및 정확한 107위 집계, 본인/타인 직접 수정 차단, 계정 삭제 조건 통과.
  • 서버 단위 검수: 점수/층/유대/시간/UID 동점 순서, 잘못된 수치·중복 ID 변경·미종료 기록 거부, 통신 실패, 삭제 계정 차단 통과.
  • WebGL 빌드 성공. 브라우저 로그인·로비·랭킹 준비 중 안내 확인.
  • 미검증: 운영 Cloud Functions 배포, 실제 App Check 인증, 운영 계정 2개 온라인 제출, 운영 닉네임 트리거와 삭제 트리거 실행. 배포 후 확인해야 합니다.
